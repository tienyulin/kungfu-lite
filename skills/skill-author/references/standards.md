# Skill 撰寫標準

寫新的 skill 與改既有的 skill 都照這份標準。

## 結構

- 一個 skill 一個資料夾：`skills/<name>/SKILL.md`，需要時加 `references/*.md`。
  只用 markdown，不放 script、不設 hook。
- frontmatter 只有 `name`（小寫、連字號）與 `description` 兩欄。
- SKILL.md 500 行內。放不下的內容拆到 references，並依主題分檔
  （agent 只會讀當下需要的那份）。
- references 從 SKILL.md 一層連到；reference 之間不再互連
  （巢狀引用會讓 agent 只讀到一半）。
- 超過 100 行的 reference 開頭放目錄。
- 多步驟流程給進度清單，讓執行的 agent 抄進回覆逐步打勾；
  複雜分支給條件式指引（「是 A 情況照下節，是 B 情況照另一節」）。

## description

這是唯一的自動觸發機制：agent 啟動時只預載所有 skill 的 name 與 description，
靠語意比對決定要不要載入 SKILL.md。寫法：

- 自然的第三人稱句，兩段語意：前半講做什麼、產出什麼；後半講什麼時候用。
- 使用者實際會說的詞要出現在句子裡，自然嵌入，不用引號列表堆疊。
  中英文講法都常見的，兩種都放。
- 只寫觸發條件與產出，不摘要內部流程——流程摘要會讓 agent 照 description
  做事而跳過 SKILL.md 本文。
- skill 之間有上下游關係的，把轉介條件寫進 description
  （例：「或 sop-to-spec 判定輸入不合格時使用」），觸發鏈才接得起來。
- 每次改完 description 都重跑觸發測試；改寫時弄丟一個觸發詞就會漏接一整類
  請求，而這只有測了才會發現。

## 行文

目標：讀起來像資深工程師寫給同事的文件。中文為主，技術名詞
（endpoint、request、response、schema、mock、repo⋯）直接用英文。

寫的時候：

- 完整句。一句話能講完的不拆成多顆 bullet；bullet 留給真正的並列項。
- 粗體只用在少數真正要強調的地方；不用 emoji；不用破折號插話尾註。
- 不自創口號與術語（「鐵律」「零猜測」「假勾」這類）；概念用平常的話講。
  必要的自創名詞（如「地標檢查」）緊接定義，且全文只用這一個名字。
- 同一概念全文同一個詞（都叫「規格」就不要一下叫 spec 文件一下叫規格書）。
- 不解釋 agent 本來就懂的事（HTTP 動詞的意義、JSON 是什麼）；
  只寫它不知道的：團隊慣例、判斷標準、範本、邊界。
- 執行經驗寫成中性提醒（「維運類 endpoint 是常見漏網之魚」），
  不寫成戰記（「實測有 agent 漏掉還回報無」）。
- 不留簡體慣用語：默認、返回、通過此、用戶、數據、信息、調用、實裝、響應。

機器掃描（skill 檔與其產出範本都掃）：

```bash
grep -rnE '默認|返回|通過此|用戶|數據|信息|調用|實裝|響應' skills/<name>/
grep -rnE '鐵律|照抄勿改|零猜測|Part [AB]|給審批|給實作' skills/<name>/
```

## 產出物

skill 產出的文件要是一份正式文件，拿給沒看過這個 skill 的人也覺得是人寫的：

- 不標讀者對象（「給審批者」「給 agent 看」這類標籤不出現在產出裡）。
- 結構照業界慣例（規格書就長得像規格書、README 就長得像 README），
  不發明只有這個 skill 才懂的節名與機制。
- 範本裡固定文字與填空明確分開：照抄的段落標「照抄」，其餘給結構與要求；
  給作者的填寫指引用範本外的說明文字承載，不混進產出。
- 產出只有交付物：skill 裡明寫不產生進度、摘要、自檢報告等過程檔案
  （弱模型常會自行留下這類檔案，須明文禁止）。

## 品質流程

寫規則時先問：這條能不能機器檢查？寫在敘述裡的規則，弱模型執行時經常漏掉；
機器檢查每次都守得住。

- 能 grep 的寫成 grep（禁用詞、引用殘留、行號引用），要求零命中。
- 能數的寫成數量比對（功能節數對 openapi operation 數、錯誤碼雙向比對）。
- 只能靠判斷的，把規則放在 agent 犯錯的位置旁邊（範本欄位裡的一句要求，
  勝過三段外的一整節說明）。

驗收紀律：

- subagent 宣稱檢查通過時，要它貼指令的逐字輸出；只回「已通過」不收。
- 產出的關鍵事實抽樣回對來源（預設值、識別字、HTTP 動詞這類容易寫反的）。
- 需要深度審查時，spawn 乾淨 context 的 reviewer 只讀產出檔，列出
  「必須猜測之處」並引原文；發現逐條分流（成立就修、駁回附理由），
  過程記錄在產出旁的 REVIEWS.md。環境開不了 subagent 時，這項降級為
  自己隔開一段工作後重讀全文，並在回報註明未經獨立審查。

一致性檢查（skill 改版最常出的問題，逐項核）：

- SKILL.md 提到的檔名、節名、清單名，在 references 裡真的存在且同名。
- 數量描述與實際相符（說「十節」就數出十節）。
- 跨檔的同一份清單（例：必要節清單同時出現在兩個 skill）內容一致。
- 上下游 skill 的介面對得上（A 的產出路徑與格式＝B 的輸入預期）。

## 測試

- 觸發測試：見 SKILL.md Step 3。負對照要含「相鄰但不該觸發」的任務
  （會議記錄之於文件 skill、bug 修復之於規格 skill）。
- 執行測試：見 SKILL.md Step 5。能開 subagent 就用可用的最弱模型試跑，
  不能就自我驗證。試跑發現的每個缺陷，修 skill 而不是只修那次產出。
- skill 會被不同家的 agent 讀（不一定是 Claude），測試步驟裡不要寫死
  特定廠牌的模型名或 subagent 機制，寫「環境裡可用的最弱模型」這類講法。
