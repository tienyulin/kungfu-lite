# Skill 撰寫

幫使用者寫新的 skill 或改寫既有 skill。開工前把進度清單抄進回覆，完成一步勾一步；
遇到本 skill 與 references 都沒定義的情況，停下來問使用者。

```
進度：
- [ ] Step 1 釐清需求
- [ ] Step 2 寫 SKILL.md 與 references
- [ ] Step 3 description 觸發測試
- [ ] Step 4 自檢
- [ ] Step 5 弱模型試跑與驗收
```

標準只有一份：[references/standards.md](references/standards.md)，動筆前先讀完。
兩個核心觀念貫穿全部步驟：

1. skill 的產出（文件、規格、程式）要讀起來像資深工程師親手寫的，skill 本身也是。
2. 寫在 prose 裡的規則，弱模型執行時常會漏；能機器檢查的規則就寫成可執行的
   檢查（grep、數量比對），放進 skill 的自檢步驟。

## Step 1 — 釐清需求

問使用者（一次問完，不要擠牙膏）：

- 這個 skill 做什麼、產出什麼？產出有固定格式嗎（有就要範本）？
- 給誰用（人透過 agent 用？agent 自主觸發？）、什麼情境會用到？
  使用者實際會怎麼開口？（收集三到五句真實講法，Step 3 要用）
- 執行時需要跟使用者互動嗎（訪談、確認），還是一路做完？
- 有沒有既有文件、範本、慣例要沿用？
- 會不會跟其他 skill 串（誰的產出是誰的輸入）？

改寫既有 skill 時，先完整讀原檔，列出要保留的功能內容（檢查項、範本、規則），
改寫只動結構與行文，功能內容不得在改寫中流失。

## Step 2 — 寫 SKILL.md 與 references

照 standards.md 的結構與行文標準寫。要點：

- SKILL.md 是流程（步驟、進度清單、何時讀哪個 reference）；大塊的範本、標準、
  對照表放 references，從 SKILL.md 一層連過去。
- 產出有固定格式的，給範本：固定文字標「照抄」，其餘給結構與填寫要求；
  給作者看的填寫指引不寫進產出物。
- 每個步驟的驗證能寫成指令就寫成指令，並要求執行後看到輸出才算通過。
- 產出物只有交付物本身：在 skill 裡明寫不產生進度、摘要、自檢報告這類過程檔案。

## Step 3 — description 觸發測試

description 是唯一的自動觸發機制（agent 啟動時只預載 name 與 description，
靠語意比對決定要不要讀 SKILL.md），寫法照 standards.md。寫完必測：

1. 準備八到十二句使用者講法：Step 1 收集的真實講法、換句話說的變形、
   不含關鍵詞的講法、容易誤觸發的相鄰任務（負對照至少三句）。
2. 先確認目前的執行環境能不能開 subagent（每家 agent 的機制不同，找得到
   對應功能就算能）。能開：spawn 兩個獨立的 subagent，模型挑環境裡可用的
   最弱一個，prompt 只給「已安裝 skill 的名稱與描述清單（含既有的其他 skill）
   ＋逐句判斷該用哪個 skill 或 none」，兩個都答對才算過。
   不能開：自己逐句判斷並寫下理由；自己寫的 description 自己判斷會偏鬆，
   在交付回報註明觸發測試是自我判定、建議之後用能開 subagent 的環境重測。
3. 漏接的句子，把它用的詞補進 description 再測；誤觸發的，收窄 description
   的適用範圍描述。

## Step 4 — 自檢

逐項做，standards.md 有完整清單與 grep 指令。重點：

- 行文掃描：AI 慣性寫法（粗體轟炸、自創口號、戲劇化警告、簡體慣用語）零命中。
- 一致性：SKILL.md 引用的節名、清單、檔名，在 references 裡真的存在且對得上；
  數量描述（「十節」「三份」）與實際相符。同一概念全文用同一個詞。
- SKILL.md 500 行內；references 引用只有一層。

## Step 5 — 試跑與驗收

skill 是給模型執行的，讀起來通順不等於執行得起來。試跑方式依環境：

- 能開 subagent：spawn 一個 subagent，模型挑環境裡可用的最弱一個
  （弱模型最會暴露 skill 的漏洞；它跑得起來，更強的模型只會更好），
  給一個貼近真實的任務，要求照新 skill 執行。親自驗收產出：逐項對 skill 的
  要求檢查，subagent 宣稱通過的檢查要求它貼指令的逐字輸出，
  不收「已通過」三個字。
- 不能開 subagent：自我驗證——自己照新 skill 從頭執行一次同樣的任務，
  嚴格照字面走、不用自己寫作時的記憶腦補；每個檢查實際執行並保留輸出，
  再逐項對 skill 的要求核對產出。在交付回報註明試跑是自我驗證。

試跑發現漏掉某條規則時，先判斷：規則能不能改成機器檢查？能就改；
不能就把該規則改寫得更靠近犯錯的位置（往範本裡放，不留在遠處的說明）。
修完 skill 再試跑一次，直到產出可以直接交付。

交付回報：skill 檔案清單、觸發測試結果（幾句全中、負對照無誤觸、測試方式）、
試跑結論與方式。
