# 怎麼寫一份好的 SOP

這份文件給提需求的人：把一個人工操作流程寫成 SOP，讓 `sop-to-spec` 把它轉成規格
（給開發和 AI 看的詳細說明書），再由 AI 照著做出 API（一個可以被系統執行的功能，
例如「刪除帳號」「查詢申請進度」）。你不用懂程式，只要把業務上的事講清楚。

空白範本在 [sop-template.md](sop-template.md)，複製它照著填。

## 為什麼要照這個格式填

AI 只看規格做事，不會回頭猜你心裡想的。規格裡「怎樣算對、怎樣算錯」的驗收條件，
全部來自你在 SOP 寫的內容；哪一格空著沒寫，AI 就得自己決定一個行為，通常跟你要的
不一樣。

## 誰負責什麼

| 角色 | 負責 | 例子 |
|------|------|------|
| 你（寫 SOP） | 這個功能的業務內容 | 做什麼、誰能用、每個參數的名稱與限制、詳細步驟、能不能復原、失敗怎麼辦 |
| sop-to-spec | 技術轉換 | 把你寫的變成規格，補上軟體該處理的機制 |
| 技術審核者 | 補技術缺口 | 回答產規格時冒出來的技術問題 |

原則：SOP 沒寫的，開發就不知道，能寫多詳細就多詳細。參數的名稱、型態、預設值、
要不要先檢查輸入，這些雖然偏開發，但只有你知道業務上該長怎樣（型態用你習慣的講法
寫就行，見下面）。只有軟體自己會處理的事不用寫：怎麼確認操作者身分（登入）、
兩個人同時操作怎麼處理、同一個請求不小心送兩次怎麼擋。

## 檔案怎麼放

在專案資料夾底下建 `docs/`，裡面建 `sops/` 和 `specs/`。`sops/` 依主題分組建資料夾，
組名自己取（`account`、`inventory`⋯）：

```
<專案>/docs/
├ sops/
│  ├ account/               ← 一組（都在處理「帳號」）
│  │  ├ delete-account.md   ← 一個功能一份 SOP 檔
│  │  └ query-account.md
│  └ inventory/             ← 另一組另開資料夾
└ specs/                    ← 產出的規格照同樣分組放這裡
```

一個功能一份檔，檔名用動作命名（`delete-account.md`）。同一組（處理同一個東西）
放同一個資料夾，不同組分開。拿不準就問自己：這些功能是不是都在處理同一個東西？

## 每份 SOP 填什麼

一個功能裡可能有好幾個步驟（例如刪帳號是停用、通知、刪資料三步）。結構是：開始前的
確認、依序的步驟（每步可帶自己的前後確認）、全部做完的確認。

各節要填什麼、填到多細，照範本裡各節的「> 提示」行，依節順序逐節填，填完把提示行
刪掉。系統層面的紀錄（log）不用你寫；只有特殊的紀錄需求（法規要求保留年限、
要出報表）才在「這個功能做什麼」提一句。

## 你填的每一格，會變成規格的什麼

| 你填的 | 會變成 | 作用 |
|--------|--------|------|
| 做什麼 | 功能的用途與範圍 | 知道在做哪件事、為誰做 |
| 誰可以用 | 權限設定需求 | 擋掉沒權限的人 |
| 特別名詞表 | 分類判斷規則 | 行話認得出來、條件判斷不出錯 |
| 相關系統表 | 介接清單 | 知道要接誰、資料去哪查 |
| 輸入表 | 參數定義與格式檢查 | 收對資料、擋錯資料 |
| 輸出表 | 回傳格式 | 回對資料 |
| 開始前先確認 | 前置條件檢查 | 擋掉不該做的操作 |
| 步驟 | 執行流程與失敗處理 | 照對的順序做，每一步失敗都有定義 |
| 怎麼算成功 | 成功情境的驗收 | 知道對的樣子 |
| 能復原嗎／能重複做嗎 | 風險等級與重複執行規則 | 危險操作多一道把關 |
| 可能出什麼錯 | 錯誤代碼表 | 知道錯的樣子、怎麼回應 |
| 測試例子 | 測試案例 | 驗證有沒有做對 |

## 填不出來怎麼辦

- 業務判斷填不出來（能不能反悔、失敗怎麼處理）：這正是只有你知道的事，
  問清楚業務再填，別留空。
- 不確定是不是真的規則：別當事實寫，句尾標「（假設，待確認）」。
  隨手猜的規則會被全部當真做出來，事後拆掉最貴。
- 參數細節寫不精確（型態不會講、名稱想不出英文、格式要問別的部門）：
  用平常的話寫、用中文取名；真的不知道的格子標「請開發補」或「待確認：問○○」，
  別整格空著。
- 軟體自己會處理的事（登入、同時操作這些，見「誰負責什麼」）：不用管，
  那是 sop-to-spec 和技術審核者的事。
