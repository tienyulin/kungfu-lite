# 怎麼寫一份好的 SOP

這份文件給提需求的人：把一個人工操作流程寫成 SOP，讓 `sop-to-spec` 把它轉成規格
（給開發和 AI 看的詳細說明書），再由 AI 照著做出 API（一個可以被系統執行的功能，
例如「刪除帳號」「查詢申請進度」）。你不用懂程式，只要把業務上的事講清楚。

空白範本在 [sop-template.md](sop-template.md)，複製它照著填。

## 為什麼要照這個格式填

AI 只看規格做事，不會回頭猜你心裡想的。規格裡「怎樣算對、怎樣算錯」的驗收條件，
全部來自你在 SOP 寫的內容；哪一格空著沒寫，AI 就得自己決定一個行為，通常跟你要的
不一樣。填得越清楚，做出來的越接近你要的。

## 誰負責什麼

| 角色 | 負責 | 例子 |
|------|------|------|
| 你（寫 SOP） | 這個功能的業務內容 | 做什麼、誰能用、每個參數的名稱與限制、詳細步驟、能不能復原、失敗怎麼辦 |
| sop-to-spec | 技術轉換 | 把你寫的變成規格，補上軟體該處理的機制 |
| 技術審核者 | 補技術缺口 | 回答產規格時冒出來的技術問題 |

原則：SOP 沒寫的，開發就不知道，能寫多詳細就多詳細。參數的名稱、型態、預設值、
要不要先檢查輸入，這些雖然偏開發，但只有你知道業務上該長怎樣（型態用你習慣的講法
寫就行，見下面）。只有軟體自己會處理的事不用寫：怎麼確認操作者身分（登入）、
兩個人同時操作怎麼處理、同一個請求不小心送兩次怎麼擋。

## 檔案怎麼放

在專案資料夾底下建 `docs/`，裡面建 `sops/` 和 `specs/`。`sops/` 依主題分組建資料夾，
組名自己取（`account`、`inventory`⋯）：

```
<專案>/docs/
├ sops/
│  ├ account/               ← 一組（都在處理「帳號」）
│  │  ├ delete-account.md   ← 一個功能一份 SOP 檔
│  │  └ query-account.md
│  └ inventory/             ← 另一組另開資料夾
└ specs/                    ← 產出的規格照同樣分組放這裡
```

一個功能一份檔，檔名用動作命名（`delete-account.md`）。同一組（處理同一個東西）
放同一個資料夾，不同組分開。拿不準就問自己：這些功能是不是都在處理同一個東西？

## 每份 SOP 填什麼

一個功能裡可能有好幾個步驟（例如刪帳號是停用、通知、刪資料三步）。結構是：開始前的
確認、依序的步驟（每步可帶自己的前後確認）、全部做完的確認。照範本的節順序填：

- **名字**：一句話，例「刪除使用者帳號」。
- **做什麼**：講清楚，不要只寫一句話——做什麼、給誰用、什麼時候用、做了之後的影響。
- **誰可以用**：哪些角色能用，清單列完整（不要寫「等」）；系統要不要強制擋沒權限的人。
- **特別名詞與分類**（選填）：SOP 裡的行話（VIP 客戶、黑名單⋯）每個都寫
  「系統要怎麼認出它」。數字類的詞也算（總金額、可用額度⋯）：怎麼算、含不含稅或折扣。
- **相關系統與資料**（選填）：過程中會串接的其他內部系統（Email、簡訊、簽核系統⋯）
  列出來，要查的資料在哪也寫，開發才知道要接誰。
- **輸入**：每個參數一列的表——名稱、型態、必填、預設值、輸入限制、說明。
  型態用你會的話寫：文字、整數、小數、是/否、日期時間、清單。
  單號或憑證類欄位（簽核單號、核准文號⋯）多寫三件事：去哪查、查到什麼才算有效、
  同一個號碼能不能重複用。某情況才必填的欄位把情況寫清楚。金額寫幣別與小數位。
  參數名稱想不出英文就寫中文，開發會取名。
- **輸出**：每個欄位一列的表。查詢類把會查到的欄位全列出來；變更類寫做完會回什麼。
  回清單的話寫排序方式、大概幾筆、全回還是回一部分。結果馬上生效還是有延遲也寫。
- **開始前先確認**（選填）：動手前業務上要先確認什麼。條件式規則兩邊都寫
  （什麼情況要、什麼情況不用）。
- **步驟**：整份 SOP 的核心，越詳細越好。人工怎麼做就怎麼寫，一步寫不清楚就拆兩步。
  每步四格：做之前先確認、怎麼做（必填）、做完怎麼確認、這步出錯了怎麼辦。
  特別留意「前面的步驟做完了、這步才失敗」的情況——整件事算什麼狀態、要不要退回。
  信件或畫面要顯示的資訊，內容從哪來也要講。處理對象有不同類型時每一種都寫。
- **怎麼算成功**（選填）：例「帳號查不到了、使用者有收到通知」。
- **做了之後能復原嗎**：能就寫怎麼復原；不能就明寫「做了就回不去」，
  以及做之前要不要額外把關。
- **同一個對象能重複做嗎**：做過再做會怎樣；做過一部分再做的規則。
- **可能出什麼錯、出錯了怎麼辦**：單一步驟的失敗寫在該步的「出錯怎麼辦」；這節寫
  跨步驟的——「開始前先確認」每一條沒過時怎麼回應；有串接其他系統的，
  「對方沒回應、不知道成功沒有」的處理方式一定要寫（等人工確認？自動再試？先鎖住？），
  這條最容易漏、也最貴；要人工接手的寫清楚誰接、怎麼接。
- **範圍外**（選填）：相關但這次不做的事，免得開發以為要處理。
- **測試例子**：想得到的情況全部列，格式是「這樣輸入，應該得到這樣的結果」。
  成功至少一個；「開始前先確認」「可能出什麼錯」與各步驟「出錯怎麼辦」的每一條
  都要有對應例子；特殊情況（空值、重複做、做一半）也列。
  這些例子會直接變成驗收依據，別跳過。

系統層面的紀錄（log）不用你寫。只有特殊的紀錄需求（法規要求保留年限、要出報表）
才在「這個功能做什麼」提一句。

## 你填的每一格，會變成規格的什麼

（讓你知道每格都有用，不是白填的。）

| 你填的 | 會變成 | 作用 |
|--------|--------|------|
| 做什麼 | 功能的用途與範圍 | 知道在做哪件事、為誰做 |
| 誰可以用 | 權限設定需求 | 擋掉沒權限的人 |
| 特別名詞表 | 分類判斷規則 | 行話認得出來、條件判斷不出錯 |
| 相關系統表 | 介接清單 | 知道要接誰、資料去哪查 |
| 輸入表 | 參數定義與格式檢查 | 收對資料、擋錯資料 |
| 輸出表 | 回傳格式 | 回對資料 |
| 開始前先確認 | 前置條件檢查 | 擋掉不該做的操作 |
| 步驟 | 執行流程與失敗處理 | 照對的順序做，每一步失敗都有定義 |
| 怎麼算成功 | 成功情境的驗收 | 知道對的樣子 |
| 能復原嗎／能重複做嗎 | 風險等級與重複執行規則 | 危險操作多一道把關 |
| 可能出什麼錯 | 錯誤代碼表 | 知道錯的樣子、怎麼回應 |
| 測試例子 | 測試案例 | 驗證有沒有做對 |

## 填不出來怎麼辦

- 業務判斷填不出來（能不能反悔、失敗怎麼處理）：這正是只有你知道的事，
  問清楚業務再填，別留空。
- 不確定是不是真的規則：別當事實寫，句尾標「（假設，待確認）」。
  隨手猜的規則會被全部當真做出來，事後拆掉最貴。
- 參數細節寫不精確（型態不會講、名稱想不出英文、格式要問別的部門）：
  用平常的話寫、用中文取名；真的不知道的格子標「請開發補」或「待確認：問○○」，
  別整格空著。
- 軟體自己會處理的事（登入怎麼驗、要不要防同時操作）：不用管，
  那是 sop-to-spec 和技術審核者的事。
