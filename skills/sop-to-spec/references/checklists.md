# 清單集

## 追問清單（Step 3，寫每條 AC 時逐題回答，答案寫進 AC —— 不准留白）

- 每個 **optional 欄位**：None 時行為？
- 每個**比較**：邊界含不含等號？
- 每個**替代輸入形式**（同一資源可用 id / 名稱 / 時間戳等多種方式指定時）：誰負責
  解析成 canonical 形式？用什麼方法？解析失敗回什麼？每個形式都要有自己的 AC
- **dry_run** response 有哪些欄位？回退資訊（操作前狀態）在 dry_run 給不給？
- dry_run 的預測範圍：執行後才知道的值（新 id、新版本號）**不預測**，明寫哪些不給
- 操作**耗時**？sync 或 202？timeout 責任在誰？
- **並發**：兩個 request 同時操作同一資源會怎樣？（狀態機擋 or 未防護＋風險說明）
- **冪等**：同一個 request 打兩次，第二次回什麼？
- **輔助性 mutation**（執行前自動修復前置條件的副作用，例如先改設定再操作）：
  必須在**其餘全部前置條件確定通過後**才執行 —— 注定失敗的 request 不得留下副作用
- 固定文案/token：spec 給字面值＋常數檔名
- **每個枚舉型欄位**（錯誤原因、狀態字…）：值域**完整列舉**在 spec 裡——寫「見某檔案」
  「等」「…」＝留白，實作者會自己發明值

## 自檢清單（Step 4）

- [ ] **概要可讀性測試**：不懂 HTTP 的主管讀完「概要」六節能說出「這個 API 做什麼、
      最危險的操作是什麼、什麼情況下會被擋」
- [ ] 概要與規格一致（「Endpoint 一覽」 = §2 總表；「人工保留項」 = §9）
- [ ] **讀者標籤掃描**（grep 全文）：`grep -nE 'Part A|Part B|給審批|給實作|給人類|給 agent' <spec>`
      —— 命中＝文件裡殘留讀者標籤/後設說明，刪掉或改寫成正式敘述，改到零命中
- [ ] SOP 每個操作都在 spec（或 Out of Scope＋原因）
- [ ] 每條 AC 可單獨驗證（確切輸入、HTTP code、欄位值）
- [ ] 每個 endpoint 的 happy/edge/failure 三類 AC 都有
- [ ] 追問清單每題每個 endpoint 都有對應 AC
- [ ] **fresh-repo 測試**：任何「比照/見/沿用」指向 spec 外（SOP 編號除外）→ inline。
      **同組其他 spec 也算 spec 外**——全文 grep「同 <另一份名>」「見另一份」這類字樣，
      有就把內容 inline 進來
- [ ] **§4 docstring 無省略**：每個 repository 方法的 docstring 含**完整**原始指令字面值
      （真實系統的實際語法，含查詢的 view/欄位名）；grep §4 有無「...」「等」式省略，有＝留白
- [ ] **mock↔AC 推演**：逐條 AC 拿 §4 mock 初始狀態手動推演 response，與 AC 期望輸出
      逐欄比對（筆數、排序、欄位值）。推演不合＝spec bug——改 mock、改 AC，或在 AC
      明寫 fixture 注入。不推演就打勾＝虛報（實測最常見的虛報就是這格）
- [ ] **矛盾掃描**（grep 全文）：§7 寫入時機不得出現與「422 不留；其餘每 request 恰好一筆」
      矛盾的句子；同一 error.status 的 details 形狀全文一致；不得殘留未定案語
      （「或另外」「待補」「下面補到」「TBD」）

## 盲審閘門（Step 5）

用 subagent 機制 spawn 一個 subagent（有 read-only 型就用它；隔離是 prompt 層約束，
選型只是加一道保險），prompt **整段照抄**（`<spec 路徑>` 換掉）：

> 你是一個實作前的 spec 盲審員，對本專案零背景。**只准讀這一個檔案：`<spec 路徑>`。
> 禁止讀任何其他檔案（包括 SOP、repo 程式碼、其他 spec），禁止搜尋 repo。**
> 任務：假設你要照這份 spec 實作，列出「實作者必須猜測或發明」的每一處。
> 每條標嚴重度：兩個合理實作者會做出不同行為 = HIGH；要自行決定並記錄 = MED；
> 純外觀 = LOW。引用 spec 原文。嚴格，不要稱讚。
> 最後另起一節回答：只讀開頭「概要」到「簽核」為止的部分，一個不懂技術的人能否
> 說出「這個 API 做什麼、最危險的操作是什麼、防護是什麼」？答不出的點列出來。

概要那節答不出 = 概要不合格，與 HIGH 同級處理。

**分流規則**：
- 每條發現**逐字對回 spec 原文**再判定；spec 已明文的 → 駁回並記理由（駁回要引原文）
- 分流時**可改判嚴重度**（reviewer 的 HIGH 實為 MED 就降級），改判要在 REVIEWS.md
  記理由；後續規則以**改判後**的嚴重度為準。「部分成立的 HIGH」若未定義行為仍存在，
  算成立的 HIGH
- 成立的 HIGH > 0 → 修 spec（**連同本輪成立的 MED 一起修**，免得下一輪重複回報）→
  **重新 spawn 全新盲審員**再審一輪，通過前不准開工
- 只有成立的 MED → 修進 spec 才開工，不強制重審
- LOW 選修
- 全部發現與處置記入 **spec 同資料夾**的 `REVIEWS.md`（例 `docs/specs/<組名>/REVIEWS.md`）

### `REVIEWS.md` 格式（沒有就建檔，每輪 append 一節）

```markdown
## <spec-slug> — 盲審第 <n> 輪（<日期>）

| # | 嚴重度 | 發現（引 spec 原文） | 判定 | 處置 |
|---|--------|--------------------|------|------|
| 1 | HIGH  | 「...」§3 未定義 X | 成立 | spec §3 補 AC-FD-7 |
| 2 | MED   | 「...」            | 駁回 | §0 已明文（引原文） |
| 3 | MED   | 「...」            | 部分成立 | 只修 response 範例，行為已定義 |

結果：HIGH 0 / MED 2 / LOW 1 → 通過（或：修 spec 後進第 <n+1> 輪）
```

## 實作回饋歸因表（Step 6）

| 歸因 | 動作 |
|------|------|
| SOP 缺資訊（錯誤碼缺漏等） | 補 SOP ＋ spec |
| skill 模板/追問清單沒問到 | 改 skill ＋ 重產 spec 該節 |
| spec 產出沒照模板 | 重產 spec 該節 |
| 純 code bug | 修 code ＋ 補 AC 對應測試 |

修完重跑 Step 4；重大修改重跑 Step 5。全程記 spec 同資料夾的 `REVIEWS.md`（歸因也 append 成一節）。
